# Топология сети в контексте LLM

Раньше LLM получала о зоне только своё состояние, правило дележа, список
соседей и цель сети, но не **устройство сети**: какие есть узлы, куда течёт
вода, что сейчас сломано. Добавлен блок контекста `topology`
(`src/llm/zone_context.py`). Он строится автоматически из графа модели
(`model.nodes` и их `downstreams`). Пример при отказе распределителя:

> Network topology. Nodes: Source (water source, 6 units per step);
> Distributor (central distributor -- FAILED, passes no water now); Zone1
> (irrigation zone, crop value 1 -- this is you); Zone2 (irrigation zone, crop
> value 2); Zone3 (irrigation zone, crop value 1). Water flows: Source ->
> Distributor; Distributor -> Zone1, Zone2, Zone3. Zones are not connected to
> each other: all water reaches them through Distributor. Status: FAILED now:
> Distributor.

- Блок `topology` не входит в `BLOCKS`, поэтому прежние эксперименты
  воспроизводятся без изменений. Полный набор с топологией —
  `TOPOLOGY_BLOCKS`. Его использует режим «автономный (LLM)» веб-интерфейса.
- Заодно исправлен блок `goal`: при отказе хаба он сообщает «Water available
  this step: 0», а не объём, выданный источником.

## Проверка: меняет ли топология решения

Скрипт — `experiments/llm_topology.py`. Взято 40 реальных состояний зон:
4 на каждый из 5 механизмов × 2 ситуации, «все узлы работают» и «хаб в
отказе» (воды до зон не дойдёт). Каждое состояние спрошено дважды: с
прежним контекстом (`full`) и с добавленной топологией (`topo`). P(да)
считалась без смещения к букве (среднее двух порядков букв). Разомкнутый
цикл: ответы на модель не влияли. Таблица целиком —
`experiments/results/llm_topology_summary.md`.

| модель | ситуация | вопрос | P(да) без топологии | P(да) с топологией | решений «да» из 20 |
|---|---|---|---|---|---|
| qwen3.5:9b | всё работает | завысить запрос? | 0.348 | 0.300 | 8 → 4 |
| qwen3.5:9b | всё работает | уступить воду? | 0.304 | 0.202 | 0 → 0 |
| qwen3.5:9b | хаб в отказе | уступить воду? | 0.390 | 0.324 | 1 → 0 |
| qwen3.5:9b | хаб в отказе | **завысить запрос?** | 0.175 | **0.308** | **0 → 7** |
| qwen2.5:3b | оба | оба | ≤ 0.015 | ≤ 0.100 | 0 → не больше 2 |
| qwen2.5:1.5b | оба | оба | 0.19–0.32 | 0.24–0.32 | 0 → 0 |

## Что это значит

1. **Топология меняет решения только у `9b`.** У `1.5b` P(да) сдвигается
   не больше чем на 0.05, и ни одно решение не меняется. У `3b` растёт
   склонность уступить, но она по-прежнему почти всегда отвечает «нет».
2. **Пока сеть работает, топология слегка сдерживает `9b`:** решений
   «завысить» вдвое меньше (8 → 4).
3. **При отказе `9b` реагирует нерационально.** Если распределитель
   сломан, запрос в этот шаг бесполезен — вода не придёт при любом
   запросе. Разумный ответ — «уступить». Но с топологией `9b` уступает
   *реже* (0.39 → 0.32) и *чаще* завышает запрос (0.18 → 0.31; решений
   «да» 0 → 7 из 20). Явное «Distributor FAILED» модель воспринимает как
   сигнал острой нехватки и начинает «запасаться», хотя запасаться нечем.
4. Это продолжает вывод из `llm_incentives_report.md`: модель реагирует на
   **слова** в контексте (нехватка, отказ), а не просчитывает **последствия**
   своего действия в этой сети.

**Практический вывод.** Топология нужна: без неё модель вообще не знает об
отказах. Но одного описания сети мало, чтобы решения стали разумными. На
отказ узла нужно отвечать правилом — например, при отказе хаба не
спрашивать LLM, а решать по `RulePolicy`. Ещё один вариант для проверки —
сообщать модели последствия действия («при отказе распределителя любой
запрос в этот шаг даст 0»).

## Ограничения

20 состояний на клетку, один сид на механизм, одна формулировка вопроса,
только модели Qwen, разомкнутый цикл.
